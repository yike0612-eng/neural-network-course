# U2 单元结项项目任务书

## 《校园课间活动建议助手：规则真的合理吗？》

**项目类型：** 个人或两人结对完成、同伴试运行的 U2 单元结项项目。  
**建议用时：** 第 8—10 课内完成，另可用 15—20 分钟完善。  
**你将交付：** 一个可运行的规则程序、一张规则决策流程图、一张测试记录表、一份规则边界反思。  
**本项目只使用教学模拟输入。** 不输入真实学生成绩、健康、行踪、行为记录、家庭信息或其他可识别个人数据。

> 你的目标不是让程序“替人决定”，而是把一组规则写得清楚、可测试、可解释，并说明它什么时候不适用。

## 一、情境与任务

学校“课间活动策划小组”想制作一个演示程序：根据**天气、可支配时间、当前任务是否完成**，给出一条低风险的课间活动建议。程序仅用于学习“规则如何影响输出”，不能作为任何人的纪律要求、成绩评价或真实活动安排。

你需要完成一个“校园课间活动建议助手”，回答下面的问题：

> “当不同的模拟情境输入到程序中时，程序为什么给出这一条建议？当两个条件同时成立时，规则应该先处理什么？程序还缺少哪些人类判断？”

## 二、允许使用的模拟输入

| 输入变量 | 示例取值 | 用途 | 程序没有看见的信息 |
|---|---|---|---|
| `weather` | `"晴"`、`"雨"` | 区分室内与户外建议。 | 实际场地安全、空气质量、学校临时安排。 |
| `free_minutes` | 5、9、10、11、20、30 | 判断时间是否足够。 | 个人意愿、真实任务难度、身体状态。 |
| `task_done` | `True`、`False` | 判断是否先提醒完成当前任务。 | 任务是否合理、是否需要教师帮助。 |

## 三、最低可运行版本

你的程序至少要有一个函数、三个以上清晰分支，并给出一条可读的建议。

```python
def suggest_activity(weather, free_minutes, task_done):
    # 请按你写出的规则补全代码
    pass
```

程序最低要求如下。

| 编号 | 要求 | 检查方式 |
|---:|---|---|
| 1 | 函数包含 `weather`、`free_minutes`、`task_done` 三个输入。 | 能说出每个输入代表什么。 |
| 2 | 至少有 3 个按优先级排列的分支。 | 流程图与代码顺序一致。 |
| 3 | 当任务未完成时，程序优先给出“先整理或完成当前任务”的建议。 | 组合测试能验证优先级。 |
| 4 | 当时间少于 10 分钟时，程序给出短时建议。 | 9/10/11 分钟边界测试。 |
| 5 | 当天气为雨且时间足够时，程序给出室内活动建议。 | 雨天测试。 |
| 6 | 程序返回建议，外部代码再负责 `print()` 显示。 | 能解释 `return` 与 `print` 的不同。 |

## 五、测试是项目的一部分

完成代码后，至少运行下列 6 组测试。运行前先写预期，再写实际输出；如果不一致，请判断是代码错误、规则优先级不合理，还是自己的预期不清楚。

| 测试类型 | `weather` | `free_minutes` | `task_done` | 运行前预期 | 实际输出 | 我从中检查了什么？ |
|---|---|---:|---|---|---|---|
| 普通 | 晴 | 30 | True |  |  | 正常户外或完整活动建议。 |
| 普通 | 雨 | 20 | True |  |  | 室内建议。 |
| 边界 | 晴 | 9 | True |  |  | 少于 10 分钟。 |
| 边界 | 晴 | 10 | True |  |  | 恰好 10 分钟。 |
| 边界 | 晴 | 11 | True |  |  | 超过 10 分钟。 |
| 组合 | 雨 | 5 | False |  |  | 任务未完成、雨天、时间短同时成立时的优先级。 |

### 两次必做改动

| 改动 | 你要预测什么 | 你要解释什么 |
|---|---|---|
| 将“时间短”的阈值从 `< 10` 改为 `< 15`。 | 哪些测试输入会改变输出？ | 规则边界改变了什么。 |
| 将“雨天室内建议”放到“任务未完成”之前，再运行组合测试。 | 输出会不会改变？ | 为什么规则顺序会影响结果。 |

## 六、规则决策流程图

画出你的程序流程。图中至少要有：输入、条件判断、分支顺序、输出建议，以及一个“需要人工判断”的位置。

```text
输入：天气、可支配时间、任务状态
              ↓
       [先判断什么？]
        /            \
      是              否
      ↓                ↓
  输出建议         [再判断什么？]
                     ↓
                  输出建议
```

请在流程图旁写一句：当 `weather = "雨"`、`free_minutes = 5`、`task_done = False` 时，箭头会怎样走？

## 七、规则边界反思

写 150—250 字，至少完成下面四句。

1. 我的程序把 ______ 放在最前面，因为 ______。  
2. 通过测试 ______，我发现/确认了 ______。  
3. 这套规则没有考虑 ______。  
4. 因此，在 ______ 的情形下，应由学生、教师或其他人补充信息并保留最终判断。

## 九、评价重点

| 关注点 | 达标表现 |
|---|---|
| 规则可解释 | 每一条分支能说明输入、条件、输出与优先级理由。 |
| 程序可测试 | 6 组测试覆盖普通、边界和组合情形；输入改变时输出可解释。 |
| 流程图一致 | 流程图的判断顺序与代码一致。 |
| 人工判断边界 | 能说明程序没有看到的信息，不把建议说成命令。 |

## 十、挑战任务

完成最低版本后任选一项挑战。挑战不会替代基础任务。

| 挑战 | 要求 |
|---|---|
| 批量情境 | 用列表保存至少 4 条模拟情境，用 `for` 循环逐条调用函数。 |
| 建议计数 | 统计“室内建议”或“短时建议”出现的次数。 |
| 规则版本比较 | 保留两种优先级方案，展示同一组组合输入为何会得到不同输出。 |
| 异常输入 | 为未知天气或负数时间增加一条透明的提示规则，并说明为什么不能猜测。 |
